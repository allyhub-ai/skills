# AllyHub

AllyHub runs, checks, previews and renders videos and decks that you write as code. How a piece looks, moves and sounds is up to you: anything a browser can draw as a function of time works. AllyHub gives you the contract below, the checks, the preview with the person's feedback, and the render.

## Run it

- `allyhub` means `npx -y allyhub` (the first run downloads it). Run commands yourself, with the workspace as the working folder. `allyhub help` lists every command in a line; `allyhub help <command>` is the reference for one: what it does, and each option with its default.
- **The workspace** is a plain folder, not a Node project: `allyhub/` in the folder you started in, or the current folder if it has `allyhub.config.ts` or `app/videos/`. Create it if it is missing; nothing is installed into it. If it has an `AGENTS.md`, follow it.
- Headless Chrome downloads itself the first time a command needs it. MP4s also need ffmpeg: if `allyhub doctor` says it is missing, give the person the install command for their system and wait; do not install system software yourself.
- In a sandbox that blocks the network, a local server or Chrome (Codex), run `allyhub` outside it: ask for that permission, or run `allyhub skill install --agent codex --global` once to write the rule. Start commands bare (`allyhub check`), with nothing in front, so the rule matches.
- Deliverables come out of `allyhub render` (the preview page's Export runs it too), so the checks apply. When AllyHub lacks something, build it inside the workspace (a component, `custom()`, a script that makes media files) rather than around it.

## The contract

These are what the build, the checks and the render depend on. Everything else is your choice.

- A piece is a module that default-exports `definePiece({ … })` from `@allyhub/sdk`. Its top level must load in Node: touch `window` and `document` only inside an output's function or a component's `mount`/`render`.
- **A frame depends only on its time.** Set every moving property in `render(t)` from `t`. The runtime virtualizes the clock, timers and `Math.random` (seeded per frame) and blocks the network; CSS animations and transitions run on real time, so do not let them drive the picture. `allyhub check` draws sampled frames out of order and fails a video whose frames differ (AK-D002).
- Put the text people see in `messages/<lang>.json` and read it with `s("<id>.<part>.<name>")`: that is what the person can edit on the preview page, and what makes each language a combo of the piece (`matrix.dims`; every combo renders in each of the piece's `formats`, so lay out by `ctx.dims`, never by the format's name). Text written in code still renders, but cannot be edited there.
- **A video is parts; a part is speech and layers.** `part({ key, speech?, dur?, layers: [...] })`: a part with speech lasts as long as it says (plus `lead` and `tail`), a part without lasts `dur`. Speech is `take(file)` (a recording, audio or video, with its words in the `.words.json` beside it: `allyhub transcribe <file>` writes them on this computer; `.range(from, to)` or `.saying(s(key))` picks the stretch a part says) or `say(s(key))` (text to speech: `allyhub voice generate` makes its file, after a quote). Layers are drawn back to front: `footage(file?)` (no file: the part's own take, in sync) and graphics (components, `custom()`), each placed with `at`/`until` as word references (`"inbox"`, `"free@2"`, `"only-0.2"`) or seconds. Parts join with cuts; a part comes in with a transition only when it asks: `transition: "fade"`, or `{ type: "push", direction: "up", dur: 0.5 }` (fade, dip, slide, push, wipe, zoom, custom). The parts keep their lengths, the window lies across the join, and the sound is not changed.
- **A batch of ads is a matrix of slots.** `matrix.slots` lists each slot's candidates (or a `pool` folder of files), and `pick`, `rules` and `differ` choose which combos to make; the output's function reads `ctx.combo.<slot>` and returns that combo's parts. Each part is rendered once and reused by every combo that has it, so a layer draws only from its props, time and words, never from another slot's pick (AK-X005). `allyhub mix` shows the chosen combos and why; `allyhub batch manifest` writes their list as CSV.
- **Talking heads: AllyHub measures, you decide the cuts.** Cut a take by its text with `.edits("./edits/<name>.json")`: it removes exactly what it lists (`remove: [{ from, to, text }]` word ranges, `sounds: [{ from, to }]` stretches of the file between words, `inWord: [{ from, to }]` stretches inside a word, `maxPause`), and places each cut itself (in the silence, at its quietest moment, on a frame); the recording never changes, and the person can strike words and sounds in the preview's Transcript. Nothing finds retakes or fillers for you, so plan from the take itself:
  1. `allyhub transcribe <take>` writes its words, bounds tightened to the sound.
  2. `allyhub transcript <take>` prints it as lines `[052.97-058.98] #161-#175 Don't guess, just go and ask. Now second, …`: a line per stretch said without a pause, word indices, and the sounds heard where no word was recognised, `(sound 61.17–61.40 0.23s −10dB v0.87)`: its stretch, length, peak against the speech, and how voiced it is (near 1 a voice: an "um" the recognizer left out, a hum before a restart; near 0 a breath). Which stretches it lists is a threshold you can change (`--sound-within`, `--sound-floor`, `--sound-min`, `--sound-voiced`); `--all` lists every stretch between words with its numbers. A sound with no silence around it is inside a word's time ("so-um" is all "so" to the recognizer): a word lasting far longer than its letters take at this take's own rate is marked `(long 0.62s ×2.4)` and listed with the voiced stretches and level dips inside it (`--word-ratio`, `--word-excess`; `--all` lists every word). Long is not a filler: a stressed word and the last before a pause are long too; an edits file cuts a stretch inside a word only when you list it (`inWord: [{ from, to }]`). Read all of it. Cut retakes and false starts, keeping the last complete attempt of a self-correction ("Now second, figure out… no. Second, find…" keeps the final "second, find…"); collapse stutters ("the goal isn't the goal isn't" keeps one); cut voiced sounds and fillers you judge distracting; shorten pauses with `maxPause`. With a script, `--script <file>` marks words in no script line and lists lines said more than once. `--search "phrase"` finds words by index; `--json` gives `words` (each `{ i, text, start, end, confidence, peak, mean }`) and `count`. You cannot listen, so the recognizer's doubt is measured for you: a word's `confidence` is the lowest probability Parakeet gave any of its tokens (`--confidence 0.8` lists the words under 0.8), and `allyhub transcribe <take> --from <s> --to <s>` hears a stretch again on its own, three times with more of the file around it each time, and prints each hearing's words beside the words file's (Parakeet can hear a close word differently by window: "observing" in one, "absorbing" in two). Which word was said is yours to judge.
  3. Write the edits file, then `allyhub edits <take> <edits.json>`: the stretches it keeps, every removal, the seconds saved and the new length, and every join measured on both sides (the seconds between the kept word and the cut, how much of that the level shows silent, the level step across it: a join with no silence on either side goes straight from one word into the next), before any render (`--pauses <s>` and `--words "um,uh"` list candidates, never applied).
  4. After rendering, `allyhub frames --cuts` draws a sheet per cut: frames around it, the waveform with silence bands, the words on each side and the sound at the cut measured. It prints each sheet's path; cuts are numbered in the whole video. `--part <key>` draws one part's cuts and joins into a folder of its own, so runs for different parts keep each other's sheets; a whole-video run replaces them all. Look for a jump, a word clipped or said across the cut, a cut with no silence on one side, and fix the edits file.
- **Two recordings of one moment** (a separate microphone and a camera, a screen recording and a webcam): `allyhub sync <reference> <other>` measures the offset between them from their sound, with how sharply they match and the drift between the two clocks; you write it into the piece (`take(mic)` for the sound, `footage(cam, { from })` for the picture; see the reference).
- `footage({ reframe: "face", punchIn: ["word"] })`, `ctx.face(t)`/`ctx.faces(t)`, layers with `z: "behind-person"` and `footage({ background: { blur: 24 } })` (the room behind the speaker blurred, dimmed, or replaced by a colour or an image) read the video's face track (every face, with ids; `footage({ speaker })` picks one) or person matte: `allyhub check`, `render` and `dev` make what is missing on this computer before going on (the first run downloads models), or `allyhub index <video>` by hand. Captions are layers you put in the parts you choose; `ctx.captions()` gives each part's cues. Where they go and which words they stress is your code: `ctx.texts(t)`, `ctx.covered`, `captionTop` and `freeAreas` measure places, `allyhub inspect --kind free-bands` gives each part's rows the speaker leaves free, `allyhub frames --overlay` draws faces, matte, covered areas and text boxes over frames, and nothing moves on its own. Formats can be platform profiles (`tiktok`, `reels`, `shorts`, `meta-feed`, `amazon`, `linkedin`), with their covered areas and length limits (an entry can change them).
- Import media, data and other files with paths relative to the importing file, inside the workspace. npm packages need a `package.json` in the workspace that declares them, and an install.
- **The render is offline**: fonts, images, footage, music and data must be files in the workspace. Bring in what the piece needs before you build (search, download, generate), each source in its own folder under `media/`, and import it.
- The type is a design choice: the stage has Inter, Noto Sans SC and Noto Color Emoji (`var(--ak-font-emoji)`, the same on every computer), and any other font works once it is in the workspace (`allyhub font add "<family>"`, or your own `@font-face`; see Fonts in the reference).
- Nothing makes a sound unless you place it: each part's speech, music (`video(…, { music })`: played once unless `loop`), sound effects a part places (`part({ sounds: [{ at, sound }] })`: the built-in whoosh, tick and pop, the look's `look.sfx` files, or any audio file), audio you write yourself with a script, the person's own files (footage keeps its sound with `audio: true`), and the paid cloud tools (see Ask first). Pick what fits the piece. `music.snap` ends silent parts on the music's beat (its tempo is measured unless you give `bpm`); `video(…, { mix, master })` sets the levels.
- A recording's words come from `allyhub transcribe` first: local, free, 25 European languages. Use the paid `transcribe-elevenlabs-scribe-v2` cloud tool, after pricing it and getting a yes, when you need what Parakeet leaves out:
  - fillers transcribed as words;
  - speaker IDs;
  - a language Parakeet does not cover.

  Find it with `allyhub tools search transcribe --refresh` and describe its input. It takes an uploaded HTTPS audio URL, or base64 bytes from a local file through `--input-file`, plus the format and optionally the language. It returns `words` as `{ w, start, end, speakerId? }`. When `alignmentStatus` is `available`, write `{ w, start, end }` to the take's sibling `.words.json`, keeping the fillers and the times. Partial or unavailable alignment is missing evidence: never invent word times.

- Components are the workspace's own code. `allyhub add <name>` copies a starter one (`titleCard`, `siteStep`, `endCard`…) into `app/components/`; change it or write your own.
- The API is in [references/sdk.md](references/sdk.md), with every default and the option that changes it. Values shown here and there are worked examples, not mandates.

## The loop

0. **When a person is watching, open the preview first**, before you research or write the piece, so they watch it take shape: create the workspace, write a first small piece (a title card with the subject's name is enough), then start the preview and leave it running. The page shows "waiting" until a piece loads, keeps the last picture while a file is mid-edit, follows the part you change, and shows every piece of the workspace as a card. Working alone (a subagent, a batch job, nobody at the screen), skip this step: the preview is for the person, and steps 1–3 are how you look yourself.
   - In Claude Code's desktop app: `allyhub launch-config <workspace> --base <the folder the session started in>` writes the entry into `<base>/.claude/launch.json`, which the app reads (without `--base`, into the workspace's own `.claude/`; it writes nowhere else, so leave `--base` out when you may not write in the session's folder); then call `preview_start` with the name it prints. The preview opens in the browser pane beside the chat, and the app runs and stops it.
   - In ChatGPT with the AllyHub app: call `allyhub_show_project` with the workspace folder; the AllyHub panel is the preview.
   - Elsewhere: run `allyhub dev --no-open` in the background and open its address in your browser pane, or give it to the person.
1. Write or change the piece, then `allyhub check` until it has no must-fix problems (fix the suggestions you can). The check reports only what is wrong whatever the taste; what needs judging it measures, and `allyhub inspect` prints those facts for you to judge (see below). To see a value inside your code (`layout(ctx)`, `ctx.face(t)`), `console.log` it: `check`, `inspect`, `render`, `still`, `frames` and `timeline` print what piece code printed after their own output, each message once with its part, layer and phase (`mount`, `render t=…`) and how many times (`--json`: `console`).
2. Look: `allyhub still --part <key> --out <png>` and `allyhub sheet --out <png>` draw frames for you; `allyhub timeline` prints the parts, where each one speaks, the line it says and the take's words it actually plays (`heard:`; compare them on a cut take), the text on screen and the sound cues. A still is a part at rest; most visual bugs are in motion, so also look at hits, cuts and transitions (`allyhub frames --at 3.1,7.05,19.8 --out <png>`), and after rendering at the file itself (`--from-render`, where motion blur and the post filter show). `allyhub audio` measures the sound you cannot hear: loudness, peaks, silences (and any inside a part's speech), and whether the cuts land on hits. `allyhub inspect` prints the facts the check measured, never verdicts: text over the speaker (shares of the face box and of the person matte), text in a platform's covered area (pixels in), text over another layer's text, how far footage is enlarged past its own pixels, at its largest and smallest over zooms and box keys (`footage({ sharpen })` helps a little; a sharper source helps more), the bands of each part's content box that the speaker's face box and person matte leave free, runs of flat frames, music against video length, the speech's loudness either side of a join, which matrix candidates the combos use, and what was done a fallback way because a measurement is missing (a face track, a matte, the music's tempo). Whether any of it is a fault is yours to decide; the kinds and their data are in the reference.
3. **Review your own render before you show it**: render it for yourself (`allyhub render`; those files are for your review, not to hand over), then `allyhub frames --cuts` (a sheet per cut), `allyhub inspect` (the facts) and `allyhub audio` (loudness, silences, where the cuts and sound effects land). Fix what you would not want seen.
4. Let the person look: the preview from step 0 is already showing your latest. They edit text there and circle what should change. In ChatGPT, the person's circled feedback comes as their message with the circled frame attached.
5. Take what they send with `allyhub feedback --wait 600` in the background (in the foreground, `--wait 90`, under your command time limit), or the `feedback` tool of `allyhub mcp`. Feedback names the piece, output, part, time, combo and format, and a screenshot in `.allyhub/agent/` with the circle drawn on it: read the screenshot first. Change what it asks, say in one sentence what you did, and wait again. A request to fix the check's problems: fix them and check again. An export: see step 6.
6. **The person exports, not you.** When the piece is ready, say so and that they can export from the preview page (Export, top right): it runs the check and `allyhub render` and shows the progress. Its files come to you through `allyhub feedback` / the `feedback` tool: give the person each file (send it into the conversation when your host can) with its full path, and do not render again. Render yourself with `allyhub render` only when the person asks you for the files, or when there is no preview page they can use (a terminal without a browser, a phone): the files go to `.allyhub/renders/<piece>/` (`--name <base>` gives them a name to share).

## Rebuilding a reference video

When the person points at a video to rebuild (a file or a link):

1. `allyhub reference <file or URL>` writes `reference/<id>/`: the video, its words, contact sheets (`sheet-01.png`…: frames every 2 s with the words said under each) and `reference.json`. It holds measurements only: cuts with scores, sentences and pauses, every place a section could start with the cut and the pause measured there, every line of text read on screen as an observation (where, how large, how long, in what share of frames, whether its words are said then), the pace, and a neutral split into segments `s1`, `s2`… by a stated rule. Nothing in it says what a stretch is for.
2. **Read the data and the sheets, and write the interpretation yourself**: `reference/<id>/interpretation.json` with your sections (`start`, `end`, `role`, `picture`, `notes`, in your own words), which lines of text are captions and which are watermarks (by id), and the caption style (the shape is in the reference). `allyhub reference reference/<id>` again labels the sheets with your sections; `--structure` prints them as parts with their durations, to start from. With `GEMINI_API_KEY` set, `--understand` asks Gemini for an interpretation of its own, marked `source: "gemini"` (see Ask first): a second opinion to check against the sheets, never a replacement for looking.
3. Write the piece with the person's product: a part per section, keyed or tagged by the section's name or role (`hook`, `demo`, `cta`…), at the reference's durations and pace.
4. Check, then `allyhub compare reference/<id> --piece <id>`: it renders (or uses the render), aligns your parts with your interpretation's sections (the neutral segments when you wrote none) and reports per section the raw differences (duration, cuts per minute, words per minute, text on screen), then a summary at a tolerance (sections within ±10 %, `--tolerance`), and a side-by-side sheet. Adjust and compare again.

## Ask first

- **Paid tools can lift the result a lot.** Spoken lines (`say`, made by `allyhub voice generate --quote`, then without `--quote`), generated images or footage, and composed music often make the difference between a good piece and a great one. Unless the person has already said no to paid tools, tell them which ones would improve this piece, what each would add, and the total estimate price for the video (`allyhub tools search <words>`, then `allyhub tools price <name> --input '{…}'` for each). Then let them choose. They cost the person's credits: get their yes before each paid plan.
- **A generated file carries its record**: a call that downloads a file writes `<file>.gen.json` beside it (the tool, the input, the credits, when, the file's sha256), and the build reads it into the media value (`gen`). Move it with the file. `allyhub tools call <name> --name <path in the workspace>` places the result there, and the same call again keeps it (nothing called or charged; `--force` calls anyway). Quote a batch at once: `allyhub tools price <name>` with several `--input`, or an `--input-file` of one JSON object per line, prints each estimate and the total. `allyhub inspect --kind generated-media` lists what each video shows or plays that is generated, and when; whether a platform's AI label is needed is for you and the person to decide.
- **Finding a tool**: `allyhub tools search` matches the words of tool names and descriptions literally, so give several at once (`allyhub tools search voice speech tts narration`). When it misses, list a group (`allyhub tools list --group media`), or run `allyhub tools catalog` and search the file it prints (one tool per line) with your own tools.
- With `allyhub mcp`, use `cloud_tools_search`, `cloud_tools_describe`, `cloud_tools_price` and `cloud_tools_call` for the same catalog. Show the estimate and get approval of the paid plan before calling; the tool returns any downloaded result file's local path (`file` names a path in the workspace for it, `inputs` prices several calls). The hosted AllyHub MCP exposes the same tools through `catalog_category_list`, `catalog_tool_list`, `catalog_tool_describe` and `catalog_tool_call`.
- **Sign-in**: when `allyhub tools` says the computer is not signed in, offer to sign in; on a yes, run `allyhub login`, show the address it prints, and wait. Never ask for or type a password or key. `allyhub login` and `allyhub doctor` name the AllyHub it talks to; `ALLYHUB_API_URL` and `ALLYHUB_WEB_URL` point it at another one (a test or local server).
- **`allyhub reference --understand` uploads the video to Google's Gemini API** (with `GEMINI_API_KEY`, then deletes it), and writes Gemini's interpretation beside your own. Fine for a public video; ask before you upload the person's own or unreleased footage.
- **Sharing is the person's to do**: never post, send or publish what you made unless they ask.
- **Facts**: never make up a number, a quote or a claim about a product. Use what the person or a source gives you, and ask when it is missing.

## When something fails

A failed command prints `error.code`, `message` and `hint` (`--json` for a structured result): do what the hint says. A check problem names its rule (`AK-…`), piece, output, combo, format, part and file position. Exit codes: 1 the check did not pass, 2 wrong usage, 3 conflict, 4 not signed in or out of credits, 5 a tool or service failed (retry), 6 not found.
